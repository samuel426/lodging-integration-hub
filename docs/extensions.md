# Extensions and Limitations

상태: Design candidates - 구현 승인 전

핵심 검색 흐름 이후에 고려할 설계입니다. 아래 내용은 현재 제공하는 기능이나 보장이 아니며, 비용과 실패 위험을 설명하기 위한 후보입니다. 상세 설정값과 구현 여부는 핵심 흐름 검증 후 결정합니다.

## 요금과 재고 cache

- 키에는 Supplier, 외부 숙소 코드 집합의 정규화된 순서, 체크인/체크아웃, 성인/아동 수를 포함합니다.
- 가격과 재고는 함께 생성된 snapshot으로 저장합니다. 서로 다른 시점의 값을 임의로 조합하지 않습니다.
- TTL은 Supplier 변경 주기와 허용 가능한 가격 오차를 측정해 정합니다. 초기값을 정하더라도 짧게 시작하고 근거를 기록합니다.
- 동일 키의 동시 miss는 single-flight로 합치고 만료 시각에 jitter를 추가해 동시 재조회를 줄입니다.
- 실패 응답이나 부분 결과를 정상 결과와 같은 TTL로 cache하지 않습니다.
- stale 응답을 허용한다면 `asOf`와 stale 표시, 최대 허용 시간을 API 계약에 추가해야 합니다.
- 검색 재고는 예약 확정이 아닙니다. 예약 직전 Supplier에 재확인이 필요합니다.

현재는 cache를 사용하지 않아 매 검색 시 원본을 조회합니다. 외부 부하가 증가하지만 만료 정책과 stale 가격의 위험을 먼저 도입하지 않습니다.

## 정규화 실패 격리

현재 제안은 유효한 offer를 유지하고 제외한 offer 수와 원인 지표를 남기는 수준입니다. 원문을 장기 보관하는 격리 저장소는 포함하지 않습니다.

확장한다면 다음을 적용합니다.

- 요청 키, Supplier, 수신 시각, 실패 분류, schema version, payload hash로 분석 단서를 구성합니다.
- 원본 전체 보관 전 API key와 개인정보 제거 여부를 검증합니다. header를 원문과 함께 저장하지 않습니다.
- 접근 권한, 암호화, 보존 기간과 최대 크기를 먼저 정합니다.
- 저장 실패가 고객 검색 응답을 막지 않도록 비동기 또는 best-effort 경계로 분리합니다.
- 재처리는 일반 저장과 분리하며 이전 정상 mapping을 덮어쓰지 않도록 검증합니다.

## 통화 변환

현재는 Supplier 통화와 최소 단위 정수를 그대로 보존합니다. 통화가 다른 금액을 직접 비교하거나 합산하지 않습니다.

환산 가격을 제공하려면 기준 통화, 환율 출처, 환율 시각, 유효 기간, 통화별 소수 자릿수와 반올림 정책을 정의해야 합니다. 계산에는 `BigDecimal`을 사용하고 원래 가격과 환산 가격을 함께 보존합니다. 환산 가격은 참고 정보이며 실제 결제 통화와 같다고 가정하지 않습니다.

## 중복 숙소와 객실 matching

현재는 Supplier별 상품을 별도로 유지합니다. 이름이 같다는 이유만으로 내부 ID를 합치지 않습니다.

향후에는 canonical stay와 Supplier listing을 분리하고 주소, 위치, 이름을 근거로 match 후보와 신뢰도를 생성할 수 있습니다. 수동 검증, 병합 해제, 이력 관리가 필요합니다. 숙소가 같아도 객실 타입과 조식, 취소 조건 등 offer 조건을 별도로 비교해야 합니다. 기존 내부 ID를 교체하는 경우 alias 또는 마이그레이션 계약도 필요합니다.

## 예약 생성과 취소

현재는 검색만 제공하며 예약 API나 예약 Entity는 구현하지 않습니다. 확장 시 검색 결과를 그대로 예약 확정으로 취급하지 않습니다.

후보 흐름:

1. 내부 예약 요청과 idempotency key를 저장합니다.
2. DB 트랜잭션 밖에서 Supplier의 가격/재고를 재검증합니다.
3. Supplier 예약 생성 결과를 짧은 트랜잭션으로 반영합니다.
4. timeout처럼 외부 성공 여부를 모르는 경우 `UNKNOWN` 상태로 두고 조회·reconciliation으로 확인합니다.
5. 실패가 확인되면 실패 상태로 확정하며, 이미 성공한 외부 예약의 보상이 필요하면 별도 취소 흐름을 사용합니다.

후보 상태는 `PENDING`, `CONFIRMED`, `FAILED`, `UNKNOWN`, `CANCEL_PENDING`, `CANCELLED`입니다. 외부 생성 timeout을 확정 실패로 간주해 무조건 재시도하면 중복 예약이 생길 수 있습니다. Supplier의 멱등성 또는 조회 수단이 없으면 자동 복구의 한계를 공개하고 운영 확인 절차가 필요합니다.

## 운영 규모 확장

- 현재 concurrency는 검색 요청당 상한입니다. 전역 및 Supplier별 bulkhead와 connection-pool pending acquire 상한은 동시 사용자 부하 테스트 후 결정해야 합니다.
- 수천 개 숙소를 모두 검색하면 batch 실행 구간이 누적됩니다. 전체 검색 deadline을 도입할 때는 실행하지 못한 batch까지 부분 실패로 알리는 계약이 필요합니다.
- 시작 시 동기화는 단일 인스턴스를 전제로 합니다. 다중 인스턴스에서는 Supplier별 lock 또는 단일 scheduler, 충돌 시 재시도와 snapshot version을 검토해야 합니다.
- 주기적 동기화는 완전한 snapshot만 원자적으로 반영합니다. 외부 pagination이 추가되면 모든 page를 검증하기 전에 누락 상품을 비활성화하면 안 됩니다.
- 현재 로컬 기본값과 mock 관리자 API는 운영 배포용이 아닙니다. 인증, 비밀정보 관리, 네트워크 경계와 운영 설정을 별도 검증해야 합니다.
