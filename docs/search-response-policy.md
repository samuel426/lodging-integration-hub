# Search Response Policy Review

- 상태: Accepted - C안, 2026-09-04 사용자 승인
- 검토일: 2026-09-04
- 정책: [POL-003](policy-decisions.md#pol-003-정규화-실패-시-응답)
- 구현 상태: 미구현. C안과 S01~S16은 승인된 실행 계약이며 실제 구현·검증 결과는 별도로 추적합니다.

## 1. 검토하는 문제

상품을 반환하지 못한 이유가 실제 품절인지, 정상 빈 응답인지, 유효한 데이터를 얻지 못한 오류인지 구분해야 합니다. JSON 파싱 성공이나 Supplier의 HTTP 200만으로 검색이 성공했다고 판정하지 않습니다.

이전 초안은 모든 offer가 잘못되어도 batch 본문을 읽을 수 있으면 200을 반환했습니다. 처리 로직은 단순하지만 고객에게 제공할 수 있는 근거가 전혀 없는 경우도 성공처럼 보이는 약점이 있어 재검토합니다.

## 2. 세 가지 대안

| 대안 | 판정 기준 | 장점 / 채택 근거 | 비용과 위험 | 검토 결과 |
|---|---|---|---|---|
| A. 본문 처리 성공 중심 | 해석 가능한 정상 envelope가 하나라도 있으면 200. 모든 offer가 거절돼도 부분 실패로 표시 | 응답 구조가 단순하고 기존 초안과 일치. 소비자가 metadata를 반드시 해석하는 환경에서 가능 | 오류 때문에 결과가 없는 것을 정상 무결과로 오인할 수 있고 HTTP 성공률이 실제 품질을 과장 | 이전 제안, 비추천 |
| B. 하나라도 오류면 전체 실패 | 일부 유효한 offer가 있어도 데이터나 호출 오류가 하나 있으면 5xx | 전체 자료의 완전성이 필요한 작업에서는 명확한 계약 | 독립적인 정상 상품까지 버리고 하나의 장애가 전체 검색에 전파. 기존 부분 성공 원칙과 충돌 | 검색에는 비추천 |
| C. 유효한 관측 결과 중심 | 유효한 상품 또는 검증된 정상 빈 결과가 있으면 200. 어느 범위에서도 판단할 근거가 없으면 5xx | 정상 결과를 보존하면서 데이터 불능 상태를 성공으로 숨기지 않음 | 정상 빈 결과, 품절 필터링, 잘못된 데이터를 별도 상태로 다뤄야 함 | 채택, 2026-09-04 승인 |

대안 C를 추천하는 이유는 검색이 독립적인 상품의 집합이기 때문입니다. 일부가 정상이라면 제공할 가치가 있지만, 전부 확인하지 못한 상태를 정상적인 상품 없음으로 표현할 근거는 없습니다. 이 선택은 모든 Supplier를 동일 시점에 완전 조회한다는 보장이 아닙니다.

## 3. 유효한 관측 결과의 정확한 의미

다음 중 하나가 있어야 정상 또는 부분 성공의 근거가 됩니다.

1. 필수 값, 요청 기간, 금액, 재고와 mapping을 검증한 offer가 하나 이상 존재합니다. 검증 후 품절 또는 인원 조건으로 제외된 정상 offer도 여기에 포함합니다.
2. 정상 envelope와 성공 상태가 확인된 availability batch가 명시적으로 빈 목록을 반환합니다.
3. 정상적으로 반영된 빈 catalog snapshot으로 해당 Supplier의 조회 대상이 없음을 확인했습니다. 이는 외부 호출 성공 batch 수에 넣지 않고 별도 상태로 다룹니다.

`items` 누락, `null`, 본문 오류, 데이터 전체 파싱 실패는 명시적인 빈 목록이 아닙니다. 임의의 빈 목록으로 대체하지 않습니다. 일부 offer만 유효한 경우 그 범위만 신뢰하며, 나머지 오류는 metadata에 남깁니다.

업무 필터링은 검증 뒤에 수행합니다. 가격이 잘못된 offer를 재고 0이라는 이유만으로 정상 품절 결과에 포함하면 전부 실패를 정상 무결과로 오판할 수 있습니다.

## 4. 추천 시나리오와 이유

아래는 승인된 C안의 검증 시나리오입니다. S11과 S12는 기존 catalog 정책을 검색 응답과 결합합니다. 아직 테스트를 실행했다는 의미는 아닙니다.

| ID | 상황 | 추천 응답 | 근거 |
|---|---|---|---|
| S01 | 모든 조회 정상, 예약 가능한 상품 존재 | 200, 상품, `partial=false` | 정상 결과를 반환 |
| S02 | 모든 조회 정상, 명시적 빈 목록 또는 유효한 상품이 전부 품절 | 200, 빈 목록, `partial=false` | 정상적으로 조건에 맞는 결과가 없음을 확인 |
| S03 | 같은 batch에 정상 상품 8개와 잘못된 상품 2개 | 200, 정상 8개, `partial=true`, 거절 2개 | 개별 오류로 독립적인 정상 상품을 버리지 않음 |
| S04 | 한 Supplier 정상 상품, 다른 Supplier timeout 또는 전부 잘못된 데이터 | 200, 정상 상품, `partial=true` | 일부 범위에서 유효한 결과를 확보 |
| S05 | 한 Supplier가 정상 빈 목록, 다른 Supplier 전부 잘못된 데이터 | 200, 빈 목록, `partial=true` | 일부 범위는 정상 무결과. 전체에 상품이 없다고 단정하지 않음 |
| S06 | 검증된 상품은 전부 품절, 나머지는 거절 또는 timeout | 200, 빈 목록, `partial=true` | 정상적으로 확인한 일부 범위는 품절이고 나머지는 알 수 없음 |
| S07 | 모든 외부 응답의 offer가 계약 위반으로 거절. 정상 빈 결과도 없음 | 502, `NO_VALID_SUPPLIER_DATA` | 외부에서 사용 가능한 데이터를 전혀 얻지 못함 |
| S08 | 일부는 잘못된 외부 데이터, 나머지는 timeout. 유효한 관측 없음 | 502, `NO_VALID_SUPPLIER_DATA` | 새 정책의 명시적 오류 우선순위. 로그에는 두 원인을 모두 보존 |
| S09 | 모든 availability 호출이 timeout, 연결 실패 또는 공급사 이용 불가 | 503, `ALL_SUPPLIERS_UNAVAILABLE` | 기존 전체 외부 조회 실패 정책 유지 |
| S10 | 외부 계약상 정상이나 모든 상품의 내부 mapping을 찾을 수 없음 | 503, `CATALOG_MAPPING_UNAVAILABLE` | 알려진 catalog 불일치. Supplier 데이터 오류라고 단정하지 않음 |
| S11 | 모든 Supplier의 catalog 성공 이력이 없음 | 503, `CATALOG_NOT_READY` | 승인된 초기화 미완료 정책 |
| S12 | 한 Supplier는 검증된 빈 catalog, 다른 Supplier는 최초 sync 실패 | 200, 빈 목록, `partial=true`, 미준비 Supplier 표시 | 정상적으로 확인한 빈 범위와 확인하지 못한 범위 구분 |
| S13 | 내부 mapper 버그 등 예상하지 못한 예외로 검색 처리를 보장할 수 없음 | 500, `INTERNAL_ERROR` | 내부 결함을 Supplier 실패나 품절로 위장하지 않음 |
| S14 | Supplier 요청 또는 인증 설정이 거부되고 다른 유효한 관측도 없음 | 500, `INTEGRATION_CONFIGURATION_ERROR` | 유효한 고객 요청을 400으로 돌리지 않고 내부 요청 생성·설정 문제로 관찰 |
| S15 | 일부 Supplier는 정상, 나머지는 호출 한도 초과 | 200, 정상 범위, `partial=true`, `RATE_LIMITED` 요약 | 가용한 상품은 보존하고 누락 원인을 구분 |
| S16 | 모든 Supplier가 호출 한도를 초과 | 503, `ALL_SUPPLIERS_UNAVAILABLE` | 현재 검색을 처리할 외부 용량이 없음. 자동 재시도는 별도 정책 |

한 Supplier의 여러 batch도 같은 기준으로 합산합니다. Supplier 단위로 성공/실패를 단순 이분화하지 않습니다. S05, S06, S12의 소비자 메시지는 '조회된 범위에는 상품이 없으며 일부 조회에 실패함'이어야 하며, '전체 품절'로 표현하면 안 됩니다. 프론트엔드 구현을 추가한다는 뜻은 아닙니다.

S14에서 Supplier가 반환한 400/401을 검색 API 호출자의 400/401로 그대로 전달하지 않습니다. 고객 요청 검증은 외부 호출 전에 끝났으며, 이후의 인증 실패는 서버 설정 문제이고 Supplier 요청 거부는 adapter 또는 mapping 문제일 수 있습니다. 단, 원인이 실제 고객 입력으로 안전하게 대응됨이 명시적으로 입증된 경우만 공개 400 규칙을 별도 정의합니다.

인증 실패가 특정 Supplier에 격리되어 있고 다른 Supplier의 유효한 결과가 있다면 200과 부분 실패를 유지합니다. 다만 운영 지표에서는 인증·설정 오류로 분리해 관찰합니다. 예상하지 못한 코드 결함으로 결과의 신뢰 자체를 보장할 수 없는 S13과 구분합니다.

## 5. 최종 응답의 판정 순서

1. 잘못된 검색 요청은 외부 호출 전에 400으로 거부합니다.
2. 예상하지 못한 내부 결함으로 계약을 보장할 수 없으면 500입니다. 공통 예외 처리에서 원인을 보존합니다.
3. catalog가 전혀 준비되지 않았으면 `503 CATALOG_NOT_READY`입니다.
4. 유효한 관측 결과가 있으면 200입니다. batch 실패, offer 거절 또는 미준비 catalog가 하나라도 있으면 `partial=true`입니다.
5. 유효한 관측이 전혀 없고 알려진 연동 설정·요청 생성 오류가 있으면 `500 INTEGRATION_CONFIGURATION_ERROR`입니다.
6. 그 외에 catalog mapping 불일치가 확인되면 `503 CATALOG_MAPPING_UNAVAILABLE`입니다.
7. 그 외에 외부 데이터 계약 오류가 있으면 `502 NO_VALID_SUPPLIER_DATA`입니다.
8. 나머지 전체 외부 이용 불가는 `503 ALL_SUPPLIERS_UNAVAILABLE`입니다.

오류가 섞인 경우의 5~8번 우선순위는 일관된 소비자 동작을 위한 프로젝트 결정이지 HTTP 표준의 강제 규칙이 아닙니다. 최종 상태 코드 하나가 유일한 원인이라는 뜻도 아닙니다. Supplier별 원인 집계를 내부 지표와 로그에 별도로 보존합니다. 분류하지 못한 내부 오류를 마지막 503으로 흘려보내지 않습니다.

## 6. HTTP 상태 코드 선택

RFC 9110은 gateway가 잘못된 upstream 응답을 받은 경우 502, 제때 응답을 받지 못한 경우 504를 정의합니다. 이 중 외부 데이터 계약 위반을 502로 처리하는 것은 이 통합 API에 적용한 설계 판단입니다. 모든 정규화 실패를 자동으로 외부 탓으로 분류하는 것은 아닙니다. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.3)

현재 승인된 전체 외부 이용 불가 응답은 503입니다. timeout만 발생한 경우 504로 더 세분화할 수도 있지만 이번 추천은 timeout에 대한 기존 계약을 유지합니다. 503은 모든 데이터 결함의 일반적인 정답이 아니며 복구가 반드시 임박했다는 보장도 하지 않습니다. 원인 분류 없이 자동 재시도하거나 복구 시각을 모르는 상태에서 임의의 `Retry-After`를 넣지 않습니다.

502 도입은 기존 '전체 실패 503'을 세분화하는 승인된 변경입니다. 데이터 불능도 503과 별도 error code로 통일하는 대안을 검토했지만, 외부 계약 오류와 일시적 이용 불가를 HTTP 계층에서도 구분하기 위해 502와 503을 나눕니다.

206은 Range 요청에 대한 부분 콘텐츠이지 일부 Supplier 성공을 나타내는 상태가 아닙니다. [RFC 9110, 206](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.7)

207은 WebDAV의 다중 자원 결과 표현에서 정의되며 본문을 해석해야 개별 결과를 알 수 있습니다. 일반 JSON 검색에 도입할 이점이 작아 현재의 200과 metadata 계약을 유지하는 것을 권합니다. [RFC 4918, Multi-Status](https://www.rfc-editor.org/rfc/rfc4918.html#section-13)

## 7. 응답과 내부 집계의 경계

추천안의 200 응답은 현재 envelope를 유지합니다.

- `data.offers`: 검증과 업무 필터링을 통과한 상품
- `meta.partial`: 일부 범위를 판단하지 못했거나 잘못된 상품을 제외했는지 여부
- `meta.rejectedOfferCount`: 개별 판정이 가능해 거절한 offer 수. 품절 제외 수가 아님
- `meta.supplierFailures`: batch 자체의 실패 요약
- `meta.unavailableCatalogSuppliers`: 성공 snapshot이 없는 Supplier

내부에는 필터링 전 유효 offer 수, 명시적인 빈 batch 수, 정상 빈 catalog 상태, 반환 상품 수, 거절 상품 수와 batch 실패를 따로 보존해야 합니다. 출력 상품 수가 0이라는 조건만으로 5xx를 결정하지 않습니다. 본문 전체를 파싱하지 못했다면 거절 상품 수를 알 수 없으므로 임의의 건수를 만들지 않고 batch 실패로 기록합니다.

추천안의 502 응답 예시:

```json
{
  "error": {
    "code": "NO_VALID_SUPPLIER_DATA",
    "message": "공급사 상품 정보를 확인할 수 없습니다.",
    "fieldErrors": []
  },
  "traceId": "example-trace-id"
}
```

5xx를 200의 빈 상품 envelope로 감싸지 않습니다. error code와 trace ID를 제공하고 API key, 외부 원문, stack trace를 고객에게 노출하지 않습니다.

## 8. 놓치면 안 되는 검증과 운영 사항

- Supplier HTTP 성공과 본문 실패를 정상 빈 목록으로 변환하지 않습니다.
- Supplier의 인증·요청 거부를 고객의 인증·입력 오류로 그대로 전달하지 않습니다.
- 알려진 입력 데이터 검증 실패만 개별 거절로 전환합니다. `NullPointerException`이나 모든 `Exception`을 무조건 거절로 흡수하지 않습니다.
- 필수 필드 누락과 세액/일자별 가격 같은 허용된 nullable 필드를 구분합니다.
- 같은 입력에서는 batch 완료 순서와 무관하게 응답 상태, 거절 건수, 실패 요약이 같아야 합니다.
- 같은 오류를 offer 거절과 batch 전체 실패에 이중 집계하지 않습니다.
- 카탈로그 부분 준비, 정상 빈 batch, 전부 품절과 잘못된 offer가 섞인 사례를 함께 테스트합니다.
- HTTP 2xx 비율과 별도로 부분 응답 비율, 유효 데이터 부재, 정규화 거절, Supplier별 실패를 관찰합니다. 검색 결과 0건 자체는 오류 지표가 아닙니다.
- alert 기준은 임의의 수치로 확정하지 않고 최소 표본 수, 지속 시간과 정상 빈 결과를 고려해 결정합니다.
- 자동 retry는 현재 범위에서 추가하지 않습니다. 특히 데이터 계약 오류는 동일 요청 재시도만으로 고쳐진다고 가정하지 않습니다.

Google SRE도 HTTP 200이지만 잘못된 내용을 반환하는 경우와 부분 실패를 별도로 관찰해야 함을 설명합니다. 이를 근거로 상태 코드만이 아니라 검색 의미에 맞는 지표가 필요하다고 판단했습니다. [Google SRE, Errors](https://sre.google/sre-book/monitoring-distributed-systems/#the-four-golden-signals)

## 9. 승인 이력과 구현 추적

- 2026-09-04: 사용자가 C안 추천과 구현 시작을 명시적으로 승인했습니다.
- API, ADR 0005, 견고성 문서를 이 정책에 맞춥니다.
- S01~S16은 통합 검색 구현 단계에서 실제 테스트와 연결합니다. 현재는 기대값만 확정된 상태입니다.
- 첫 구현 단위는 catalog mapping이며, 검색 API가 이미 제공된다는 의미는 아닙니다.
