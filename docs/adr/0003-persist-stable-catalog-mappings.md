# ADR 0003: 안정적인 catalog mapping 영속화

- 상태: Accepted - 정책 범위
- 제안일: 2026-09-03
- 승인일: 2026-09-04

UUID mapping 영속화와 기존 mapping 보존 원칙은 Gate 1에서 승인되었습니다. 2026-09-04에 사용자가 소프트 삭제와 catalog 부분 준비 정책을 승인했습니다. [POL-001/002](../policy-decisions.md)에 승인 근거와 검증 항목을 기록합니다. 상세 schema와 전체 Gate 2, 도메인 구현 시작까지 승인된 것은 아닙니다.

## 배경

Supplier의 외부 코드는 내부 API 식별자로 직접 노출하기에 불안정하고 공급사별 범위가 다릅니다. 반복 동기화, 상품 정보 변경, 일시적인 catalog 장애에도 내부 식별자는 유지되어야 합니다.

## 결정

숙소와 객실 타입에 UUID 내부 ID를 발급하고 Supplier 외부 키와의 mapping을 PostgreSQL에 저장합니다. 성공한 전체 snapshot에서 사라진 mapping은 삭제하지 않고 비활성화하며, 다시 등장하면 기존 UUID로 재활성화합니다.

Supplier별 동기화 상태도 저장합니다. 빈 catalog를 정상 반영한 경우 성공으로 기록하고, 모든 Supplier에 성공 이력이 없을 때만 검색을 준비되지 않은 상태로 판단합니다. 일부만 준비된 경우에는 검색 응답에 미준비 Supplier를 표시합니다.

## 결과

- 동일한 외부 키는 반복 동기화 후에도 같은 내부 ID를 사용합니다.
- 삭제 후 재등장한 상품도 기존 ID를 복원할 수 있습니다.
- 외부 호출과 DB 반영을 분리하고 Supplier snapshot 단위로 원자적으로 반영합니다.
- sync 상태 테이블과 비활성 데이터 관리가 추가됩니다.

## 검토한 대안

- 요청 시 ID 생성: 호출마다 식별자가 달라질 수 있습니다.
- 외부 코드 직접 노출: Supplier 교체와 코드 변경이 API 계약에 전파됩니다.
- 물리 삭제: 재등장 시 식별자 연속성을 잃습니다.
