# AI Usage Log

AI를 요구 분석, 설계 대안 검토, 코드·테스트 작성, 문서 정리와 검증에 사용했습니다. 아래 수용·수정·거부는 제안을 평가한 기록이며 AI 생성 자체를 검증으로 보지 않습니다. 날짜별 승인 대기나 미구현 표기는 당시 상태입니다. 현재 상태는 [구현 현황](implementation-plan.md)에 정리합니다.

## 원칙

- AI가 제안한 버전과 API는 공식 문서에서 다시 확인합니다.
- 설계 선택은 대안과 손실을 기록한 뒤 사용자가 승인합니다.
- 생성된 코드는 컴파일, 테스트, 포맷 검사로 검증합니다.
- 이해하거나 설명할 수 없는 코드는 수용하지 않습니다.
- 외부 원문을 저장소 문서에 복사하지 않습니다.
- 검증 결과와 남은 불확실성을 사실대로 기록합니다.

AI가 먼저 제안한 기준도 반례가 발견되면 유지하지 않습니다. 이번에는 본문 파싱 성공이 검색 의미의 성공을 보장하지 않는 점을 확인하고 제안을 수정했습니다. 사용자의 질문을 정책 승인으로 간주하지 않고 대안 비교 상태로 기록했습니다.

### 후속 승인과 구현 재개

같은 날 사용자가 C안 추천을 승인하고 구현 시작을 요청했습니다. 유효 관측 기반 응답과 502/503 구분을 수용했으며, 이전 보류 상태를 해제했습니다. 최초 구현은 catalog 단위로 분리하고 정상·빈 snapshot·실패·재활성화·트랜잭션 경계를 검증합니다. PMD로 오류 패턴을 분석하고 실행 JAR의 의존성 취약점 검사 범위를 확인합니다. 검색 시나리오는 아직 구현 완료로 기록하지 않습니다.

### Catalog 구현과 검증

| 목적 | AI 지원 | 수용·수정 판단 | 실제 확인 |
|---|---|---|---|
| 안정적 ID | 전체 snapshot upsert와 비활성 mapping 재사용 | 승인된 POL-001 구현으로 수용 | 반복·변경·삭제·재등장 DB 테스트 및 JAR 재기동 |
| 실패 격리 | 외부 호출 밖 트랜잭션, Supplier별 원자적 적용 | `NEVER`/`REQUIRES_NEW`, 읽기 `REPEATABLE_READ`로 구체화 | 실패 rollback, 다른 Supplier commit, 기존 트랜잭션 호출 차단 |
| 계약 검증 | 명시적 빈 목록과 누락/오류 분리 | 자동 기본값·숫자 coercion은 거부 | A HTTP/B 본문 오류, 필수 필드·타입·중복·크기 테스트 |
| 초기 호출 지연 | 네트워크 런타임 warmup | 요청 시간 제한은 유지, 실제 Supplier 호출 없이 초기화 | 첫 호출 TIMEOUT 반례 기록 후 전체 61건 재검증 |
| 정적 분석 | PMD 규칙 적용 | 생성자 메서드 호출 수정, 정책상 nullable reset만 좁게 억제 | PMD main/test 통과 |
| 테스트 작성 | 독립 WireMock fixture와 PostgreSQL 시나리오 | AI의 문자열 상수화 과정에서 깨진 JSON 수정 | 전체 테스트 61건 2회 통과 |
| 보안 검사 | 실행 JAR 의존성 확인 | `fs` 빈 검사 결과를 거부하고 `rootfs`로 교정, Tomcat 패치 | 패치 후 HIGH/CRITICAL 0건 |

검색 응답의 C안은 문서 계약만 확정했으며 실제 HTTP 테스트는 후속 단계입니다. 높은 현재 코드 커버리지와 전체 기능 완성을 혼동하지 않습니다. 상세 실패·수정 과정은 [작업 기록](../JOURNAL.md)에 남깁니다.

## 2026-09-06 - HTTP 및 로그 경계 보완

AI가 이전 테스트 통과와 별개로 본문 절단, 중복 JSON 필드, JDBC 실패 로그를 추가 확인했습니다. 단순히 예외를 모두 잡는 제안은 사용하지 않고 알려진 네트워크 오류만 분류합니다. JSON 필드 중복 검출과 DB 상세 오류 제한은 승인된 snapshot 보존·비노출 정책을 충족하기 위해 수용했습니다. 실제 HTTP와 PostgreSQL, 출력 캡처 테스트로 검증하며 환경 초기화 실패도 JOURNAL에 남깁니다. 당시 Swagger에 검색 API가 없던 것은 Controller 미구현 상태였으며, 문서 UI 존재를 기능 구현 완료로 기록하지 않습니다.

## 2026-09-06 - Availability adapter 경계

- 목적: 승인된 가격·재고 정책을 구현하고 공급사 오류가 정상 빈 검색으로 변환되지 않도록 검증.
- 수용: 원시 JSON의 상품 단위 변환, checked arithmetic, 명시적 빈 batch 상태, 요청 목록 분할.
- 수정: HTTP URI에 CSV를 문자열로 연결하는 대신 URI template 인코딩과 구분자 검증을 사용.
- 거부: 모든 RuntimeException을 공급사 오류로 흡수하는 처리. 내부 결함은 별도 500으로 전달해야 합니다.
- 검증: 정규화 단위 테스트, 실제 HTTP 계약 테스트, 기존 catalog/본문 중단 회귀와 PMD 검사를 실행합니다.

AI 활용 여부보다 제안을 어떻게 검증하고 판단했는지를 기록합니다. AI가 만든 결과는 공식 문서, 실행 결과, 테스트 또는 사용자 검토 중 하나 이상으로 확인합니다.

## 수용하지 않은 접근

### Spring Boot 3.5.16 유지

익숙한 계열이라는 장점이 있었지만 마지막 OSS 릴리스라는 공식 안내를 확인했습니다. 새 프로젝트의 유지보수성과 기술 선택 근거를 고려해 사용하지 않았습니다.

### 전면 WebFlux

외부 호출 외의 요청 처리와 DB 접근까지 reactive로 전환할 필요가 없었습니다. JPA를 유지하면서 전체 stack을 WebFlux로 구성하면 blocking 경계가 복잡해지므로 채택하지 않았습니다.

### H2 기반 테스트

빠르지만 PostgreSQL과 다른 타입 및 제약조건 동작으로 인해 매핑 무결성 검증의 신뢰도가 떨어질 수 있어 사용하지 않았습니다.

### 별도 Spring Boot mock 애플리케이션

동적 제어는 편리하지만 애플리케이션 수와 유지 범위를 늘립니다. WireMock scenario와 fixture만으로 필요한 실패 상태를 재현하기로 했습니다.
